## 1. What you found

### The client's need

Onward Logistics needs to give each new engineer exactly the access their job requires from day one. The process has to work the same way every time, nobody should be able to quietly gain more access than their role allows, and the company must be able to show who changed access and when.

### Solutions that exist

| Solution | How it works | Trade-off for this client |
|---|---|---|
| **1. Manual set-up in the AWS Console** | An administrator creates each user by hand, picks policies and emails a password. | **Strength:** quick to start, no tooling or skills needed. **Weakness:** every hire is set up slightly differently, mistakes and over-permissioning are common, and there is no reviewable record of *why* access was granted. |
| **2. AWS IAM Identity Center with a corporate identity provider** | Engineers sign in through single sign-on and receive short-lived credentials from permission sets mapped to their job. | **Strength:** AWS's recommended pattern for people. No long-lived passwords in AWS, and joiners and leavers are handled centrally. **Weakness:** needs AWS Organizations and an identity provider integration, which is a larger change than the client needs to solve today's problem. |
| **3. Infrastructure as Code: IAM groups and permission boundaries deployed from Git with CloudFormation** | Roles, users, guardrails and audit logging are defined in a template. Every change goes through Git and is applied automatically by CloudFormation Git sync. | **Strength:** identical, reviewable and repeatable onboarding with a full change history, and the boundaries cap access even if someone over-grants later. **Weakness:** it still uses IAM users with long-lived passwords, and the team needs basic Git and CloudFormation skills. |

### What happens with no solution

If access stays ad hoc, Onward Logistics carries risk in four areas:

- **Security breach and financial loss.** Over-broad permissions turn a small mistake into a major incident. In the 2019 Capital One breach, an over-permissioned role let an attacker read data on about 100 million customers. Regulators fined the bank USD 80 million, and it later settled class-action claims for USD 190 million.
- **Operational disruption.** In 2018 a former Cisco engineer whose cloud access had not been removed deleted 456 virtual machines that supported WebEx Teams. Around 16,000 customer accounts were affected for up to two weeks, and the clean-up cost Cisco about USD 1.4 million. For a logistics company, a similar outage could stop shipment tracking and dispatch.
- **Loss of customer trust.** Partners and shippers expect their data to be handled securely. A publicised incident damages contracts and renewals.
- **Legal and audit exposure.** Without a log of who granted access and when, the company cannot prove control to auditors or investigators, and that weakens its position under data-protection rules.

## 2. The business value of your solution

### Your chosen approach

I chose **Solution 3: onboarding defined as code in Git and deployed automatically with CloudFormation Git sync.**

It fits Onward Logistics best because it solves the actual problem, which is consistency, least privilege and auditability, without requiring a new identity provider or a multi-account restructure first. Each job function (storage engineer, compute engineer, on-call observer) is defined once and reused for every hire, so two people in the same role always get the same access. Permission boundaries act as a hard ceiling: even if someone later attaches an administrator policy to an on-call engineer, that engineer still cannot launch or terminate servers. Every access change is a reviewed Git commit, and CloudTrail records every change made in AWS, so the company can answer "who changed access, and when?" from two independent records.

This design also prepares the move to IAM Identity Center (Solution 2). The same job-function definitions can later become permission sets.

### Services you will use

| Service | The job it does | Why this service, used this way |
|---|---|---|
| **AWS IAM: groups with AWS managed policies** | Defines each job function (storage, compute, on-call observer) and grants its permissions to members. | Managing access per role instead of per person keeps onboarding consistent. AWS managed policies are maintained by AWS, and no inline policies are used, so permissions stay visible and reusable. |
| **AWS IAM: permission boundaries** | Sets the maximum access each engineer can ever have, whatever is attached later. | This is the guardrail against privilege creep and mistakes. The on-call boundary also explicitly denies creating, starting or terminating compute, and blocks users from removing their own boundary. |
| **AWS IAM: users with forced password reset** | Gives each engineer a console identity that must set a personal password at first sign-in. | Nobody, including the administrator, knows the engineer's working password after day one. |
| **AWS Secrets Manager** | Generates a strong random first-login password for each new user. | Passwords are never typed by a person, sent in chat or committed to Git. CloudFormation reads them directly from Secrets Manager at deploy time. |
| **AWS CloudFormation** | Builds all users, groups, boundaries and audit resources from one template. | The same template produces the same result every time, and changes are previewed as change sets before they are applied. |
| **CloudFormation Git sync (AWS CodeConnections)** | Deploys the template automatically whenever the approved Git branch changes. | Git becomes the single source of truth, which gives peer review and a permanent history of every access decision. No one makes manual changes in the console. |
| **AWS CloudTrail** | Records every API call, including IAM changes, across all Regions in a log bucket. | Gives tamper-evident evidence (log file validation is on) of who changed access and when, for security reviews and audits. |
| **Amazon S3 (audit log bucket)** | Stores the CloudTrail logs. | Versioned, encrypted, blocks all public access, denies non-HTTPS requests, and is kept even if the stack is deleted, so the audit evidence survives. |
| **IAM service roles for deployment** | Separate roles for Git sync and for CloudFormation to act on the client's behalf. | People do not need standing permission to change IAM. The pipeline does it through a defined role. |

### Who benefits, and how you will know

| Stakeholder | Benefit | How you would know |
|---|---|---|
| **Head of Security** | Can prove that every engineer has only the access their role allows, and can see who changed access and when. | `verify-access.sh` shows "allowed" for in-role actions and "denied" for out-of-role actions. Even after Administrator access is attached during the stress test, the on-call engineer is still denied `ec2:RunInstances`. CloudTrail returns the matching attach and detach events. |
| **Platform / Cloud Administrators** | Onboarding becomes a reviewed Git change instead of a sequence of manual console clicks. | Time to onboard a new engineer drops from a manual process to a single merged commit. Console-made IAM changes outside the pipeline fall to zero, which can be checked in CloudTrail. |
| **New engineers (storage and compute)** | They can work on day one with the right tools, and get a secure first sign-in. | Each new hire signs in on day one, is forced to set their own password, and raises no access-related support tickets in their first week. |
| **On-call engineers** | They can see the health of servers and storage during incidents without the risk of accidentally stopping production. | Simulator results confirm read access is allowed and all create, start and terminate actions are denied. No incidents are caused by on-call staff changing compute. |
| **Engineering / Operations leadership** | Lower risk of outages and data incidents, and audit readiness without extra effort. | Audit requests for access history are answered from Git and CloudTrail within the same day. There are no audit findings on uncontrolled access. |

### Limits and risks of your design

- **Long-lived IAM users.** The design uses IAM users with passwords instead of short-lived single sign-on credentials. AWS recommends IAM Identity Center for people, and that is the planned next step.
- **MFA is not yet enforced.** The template does not require multi-factor authentication. A stolen password would still give access within the user's boundary. MFA should be required, for example through a boundary condition on `aws:MultiFactorAuthPresent`.
- **Broad permissions within each role.** The storage and compute boundaries allow `s3:*` and `ec2:*` on all resources. Production data is protected by role separation but not by resource-level scoping, such as restricting access to specific buckets, tags or Regions.
- **The pipeline itself is powerful.** The CloudFormation deploy role has wide IAM rights, so anyone who can merge to the deployment branch can change access. Branch protection, mandatory reviews and limiting who can merge are essential.
- **Manual password hand-off and no automated offboarding.** An administrator still delivers the first password out of band, and the generated secrets remain after first sign-in. Removing a leaver depends on someone editing the template. Both steps should be automated.
- **Logging without alerting.** CloudTrail records changes but nothing raises an alarm. A CloudWatch or EventBridge alert on IAM policy changes would let the security team react within minutes instead of finding problems in a review.
- **Scale.** Users are named individually in the template, which suits a small team but becomes unwieldy as the company grows. It also covers a single AWS account only, not a multi-account organisation.
